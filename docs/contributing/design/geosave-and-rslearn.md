# GeoSave and rslearn, from satellite image to trained model

*Architecture review · 20 November 2026*

**GeoSave’s biggest strength is that a researcher can start with their own experiment and contribute just the part another project can reuse.** Someone with aligned image and label files can borrow the chipper, keep their PyTorch Dataset and try a different training method in ordinary Lightning code. If the method works, the same code can become an editable recipe for the next researcher. Someone who only wants the resulting map can load a published raster pipeline and pass it an xarray object. Each person can enter at the point relevant to their work. [Chip extraction][gs-chip] · [Workspace generator][gs-workspace] · [Raster pipeline release](../../advanced/release.md)

**rslearn’s biggest strength is what the user gets by adopting its dataset.** Give a training example a persistent identity as a *window*, and source discovery, labels, splits, model inputs and predictions can all refer to the same thing. A new project can inherit years of work on those connections. GeoSave has strong individual operations, but the user still has to make several of those connections in each project. The most valuable improvement would be a supported path from paired imagery and labels to a trained model that someone else can reload and use to make a map. [rslearn core concepts][rs-core] · [rslearn land-cover quickstart][rs-quick] · [GeoSave training recipes][gs-recipes]

## The same land-cover project, with two starting points

Imagine a team that wants a land-cover map for a new city. One colleague has a bounding box and dates. Another has already spent weeks producing aligned image and mask GeoTIFFs. The choice of library looks different from each desk.

**From an area and dates, rslearn has the more complete starting point.** Its quickstart creates 128 × 128 windows on a 10 m grid over Seattle. A Sentinel-2 layer looks up imagery and an ESA WorldCover layer supplies labels. Both support direct reads from cloud-optimized files. `prepare` records which source items match each window. `materialize` crops, reprojects and mosaics their pixels. A model configuration connects the ordered Sentinel-2 bands and target layer to OlmoEarth Nano, a U-Net decoder and a segmentation head. After fitting, the tutorial creates a Portland prediction window, attaches a writer, loads a checkpoint and writes the predicted layer. The user supplies substantial configuration, but can complete this specific workflow without writing a Dataset, training loop or geospatial writer. [Acquisition and labels][rs-acquire] · [Model and fit][rs-fit] · [Prediction and splits][rs-predict]

There is a scientific decision left to the user. The first version of the tutorial uses the same windows for training and validation. A later section assigns split tags by hashing window names. That makes assignment repeatable, but nearby windows can still share landscape, imagery and acquisition conditions. For an estimate of performance in a new city, split by scene or geography before drawing chips. There is also a date mismatch worth noticing. The example requests imagery from summer 2024 and uses WorldCover 2021 as the target. A new development between those dates can be perfectly aligned to the grid and still have the wrong training label. Both decisions belong to the experiment. [Quickstart acquisition][rs-acquire] · [Split example][rs-predict] · [WorldCover source][rs-worldcover]

**From prepared rasters, GeoSave has the more direct entry point.** A file opens as an xarray object. An existing Dataset can enter at the same point. The caller can inspect or change a band using ordinary xarray, or hand the data to a released pipeline. Compare this with rslearn’s own EuroSAT example. To bring existing GeoTIFFs and class labels into its standard training path, that example constructs one window per image, writes the image and a label feature, and marks the layers complete. This work buys subsequent enrichment, sampling and consistent output writing. It is substantial when the immediate job is to try a model on a raster that is already correct. rslearn also supports local files and programmatic writes, and its materialized GeoTIFFs remain usable in GIS tools. [GeoSave openers][gs-io] · [rslearn EuroSAT conversion][rs-eurosat] · [rslearn dataset format][rs-format]

Here is the GeoSave inference call for an existing, compatible single-scene GeoTIFF. The release expects a node called `image` and includes a dense segmentation postprocessor. The same call accepts an image assembled from native STAC Items.

```python
import geosave as gs
import xarray as xr
from geosave.ml.release import load_pipeline

pipeline = load_pipeline("release")
with gs.open_raster("scene.tif", chunks={}) as image:
    rasters = xr.DataTree.from_dict({"image": image})
    land_cover = pipeline.predict(rasters)
    class_map = land_cover["class_id"]       # xarray.DataArray on the scene grid
```

The entry point is small because the release carries the preprocessor, prediction strategy and decoder. An optional ingestor can produce the same tree from a region. The caller decides when to invoke it. GeoSave already tests prediction from supplied rasters and equivalence after saving and reloading a pipeline. This example assumes compatible band names and pixel meaning. That assumption is one of the most important weaknesses below. [Pipeline implementation][gs-pipeline] · [Release round-trip tests][gs-pipe-tests]

**The two libraries can also share a file.** I opened the actual prediction GeoTIFF written by rslearn’s offline segmentation test directly with `gs.open_raster`. GeoSave returned a chunked 32 × 32 `uint8` band in EPSG:4326 on the target’s exact grid. I compared every pixel with `window.data.read_raster(...)` in rslearn. All 1,024 matched. There was one revealing difference. rslearn could request the band as `class` using its layer configuration. Opening the TIFF alone gave GeoSave the name `band_1`. The grid and values traveled through the file. The meaning of that band lived in the dataset configuration. A team can therefore use rslearn to prepare data and GeoSave to analyze it, provided it carries the relevant names and class legend across that handoff. [rslearn prediction fixture][rs-seg-test] · [GeoSave file reader][gs-io]

## Where each library puts the state

| Stage | rslearn’s standard workflow | GeoSave’s standard building blocks |
| --- | --- | --- |
| Identify the example | A persisted Window names a group, location, pixel bounds, projection, time interval and options such as split tags. | A GeoRegion describes a request and an ODC GeoBox places pixels. In the Dynamic World example, a project-owned `scene.parquet` already records each annotation’s split, paths and date. Several annotations can share one image. [Teaching dataset layout][gs-scenes] |
| Acquire data | A configured layer asks a DataSource to match source Items to windows. Item groups are recorded. A tile store can reuse downloads across windows, or a provider can materialize directly. | A STAC client or GeoParquet table finds native Items. ODC loads selected assets onto a requested grid. A product-specific ingestor can assemble named xarray nodes. Saving data is an explicit choice. |
| Read a training example | ModelDataset reads eligible window layers. DataInput selects layer groups and bands. Task constructs task-specific inputs and targets. | A project-owned PyTorch Dataset selects images, labels and context. GeoSave handles operations such as decoding, cropping and conversion to tensors. The project defines the sample returned to Lightning. |
| Run the model | The standard model receives ModelContext, including per-example inputs and metadata. Its final predictor can see targets and returns outputs and losses. | ModelChain routes named values between PyTorch stages. A project LightningModule owns the objective. Dense inference calls the model with named batched tensors. |
| Deliver a result | A Task interprets the output. A writer can merge crops and write a named window layer, including into a separately configured destination. | A postprocessor turns merged output into a product. Dense built-ins produce xarray Datasets. The caller can inspect, export, or predict chunk by chunk into Zarr. |

The rslearn interfaces are individually replaceable. A team can add a source, compositor, storage backend, model or task by class path at the appropriate point. The coupling comes from **the information those interfaces exchange**. Window identity reaches from preparation into model sample metadata and on to the writer. GeoSave’s equivalent handoffs mostly use objects already understood by another library. A custom training project can leave after `.gs.to_tensor()`, and a raster can enter just before prediction. In return, GeoSave has no shared owner that can answer “which exact images and labels made up the training set?” across projects. [rslearn source interface][rs-source] · [Model context][rs-context] · [Prediction writer][rs-writer] · [GeoSave architecture](../architecture.md) · [Sample records under discussion](samples-chips.md)

### How much work each project delegates

Both projects delegate substantial work. An rslearn direct-materialization adapter uses Rasterio’s `WarpedVRT` for reprojection. Training uses PyTorch, Lightning and TorchMetrics. Sources can use STAC and provider SDKs. What rslearn implements itself is the **dataset lifecycle** that turns those operations into a repeatable job across many windows. GeoSave calls `odc.stac.load` and keeps its xarray Dataset, then adds information the next consumer needs, including observation periods and selected metadata. Its Sentinel-2 integration still has to implement provider asset aliases, processing-baseline offsets, selection of reprocessed tiles and categorical SCL resampling. Delegation saves GeoSave from maintaining a raster engine. It cannot supply scientific meaning that a provider omitted or expressed differently. [rslearn reprojection][rs-warp] · [rslearn dependencies][rs-deps] · [GeoSave ODC loader][gs-load] · [Sentinel-2 ingestion][gs-s2]

GeoSave also has coupling of its own. Multi-stage model assembly uses named, typed step declarations, and the standard dense predictor expects pixel inputs it can chip on a common grid. Those constraints matter when deciding which part of an experiment other people can reuse. [Chain routing][gs-routing] · [Dense predictor][gs-dense-predict]

### From a local experiment to a pull request

Suppose the land-cover researcher tries a cloud mask. They can apply it to one scene in xarray, inspect which pixels it removes, then move the operation into a project preprocessor so training and inference see the same imagery. If the model uses registered GeoSave stages, they can package the trained chain and its raster processors with `ChainModel.from_pipeline(pipeline)` and publish it with `push_to_hub`. A colleague can install the researcher’s package and reload the pipeline. The release records a custom processor’s import path and constructor arguments, so the package must make that class available. The team can share the result before deciding whether the mask belongs in GeoSave. [Preprocessor contract][gs-prep-base] · [Publishing and reloading](../../advanced/release.md) · [Release reconstruction][gs-release]

What goes into a pull request depends on what proved useful in the experiment.

| What another project wants to reuse | What the researcher can contribute |
| --- | --- |
| **The model or encoder** | Contribute the model implementation as a registered component with its construction arguments and named inputs. Someone can then select it in a different experiment and release its trained weights. A new project-local stage can be tried in Python, but the current GeoSave release format requires that stage to be registered and defined in the library. For a novel encoder, upstream integration comes before a reloadable GeoSave release. [Encoder example][gs-small] · [Release checks][gs-release] |
| **The training method** | Contribute an editable task recipe containing the LightningModule, configuration and any Dataset or DataModule behavior the method needs. The next user gets a local copy they can adapt. A researcher who only wants the trained model can use the inference release independently of those training files. [Training recipes][gs-recipes] · [Workspace generator][gs-workspace] |
| **The raster-to-map pipeline** | If the cloud mask is the reusable idea, contribute that preprocessor and show how it works with the existing predictor and postprocessor. If the valuable result is the particular combination of imagery, model and class decoder, share the configured pipeline and a worked example. The project’s scene splits and experiment logger can stay with the training code. [Raster pipeline][gs-pipeline] · [Pipeline round-trip tests][gs-pipe-tests] |

### What a second data source actually costs

Consider adding elevation to the optical image. In rslearn a team can select a cataloged DEM, declare a layer and its resampling policy, and have the existing windows materialized again. Its catalog also reaches into different kinds of systems, including ERA5-Land climate data, SoilGrids via WCS and OpenStreetMap features from PBF. For HLS, the NASA integration even exposes common optical band names across Landsat and Sentinel observations. That lets a caller request one optical input even when the original Landsat and Sentinel assets use different identifiers. [Source catalog][rs-sources] · [HLS cross-sensor bands][rs-hls]

In GeoSave, a DEM that already exists as a suitable raster needs no new source class. The caller can load it onto the image's GeoBox, inspect the result and put it beside the image in a DataTree. The stock DensePreprocessor prepares bands from one named node, so a two-input model needs preparation that keeps both. Someone must also choose the elevation units, resampling, missing coverage and what to do when training and serving use different copies of the DEM. This is where adding a *tested two-input recipe* teaches more than adding another catalog URL. A format or provider SDK can own access. The recipe must still establish what values the model receives. [GeoSave grid loading][gs-load] · [Single-node dense preprocessor][gs-prep] · [Named predictor inputs][gs-dense-predict]

## Input correctness has several owners

The closest rslearn names are **DatasetConfig**, **DataSourceConfig** and **DataSource**. Comparing those three directly with GeoSave’s **RasterIngestor** hides the most important distinction. The first describes the dataset, the second configures retrieval for a layer, and the third implements it. rslearn has another interface, **DataInput**, for the training consumer. GeoSave’s ingestor mainly determines which raw rasters a release receives for a region. Its Sentinel-2 implementation also exposes exact-grid loading, useful when a training label already defines the grid. [rslearn configuration][rs-config] · [DataSource][rs-source] · [DataInput][rs-input] · [GeoSave ingestor][gs-ingestor] · [Exact-grid ingestion][gs-s2]

| Question | What rslearn checks | What GeoSave checks today |
| --- | --- | --- |
| Is the declaration coherent? | The Pydantic configuration rejects unknown top-level fields, requires band sets for a raster layer and checks how each band set is specified. | BuildSpec validates component selection. Sentinel2Ingestor checks supported bands and catalog. ModelChain resolves declared stage inputs and outputs. Pipeline wiring alone cannot detect wrongly scaled pixels. |
| Can this example supply the input? | Required layer availability can exclude a window with a recorded reason. An unresolved requested band can still fail when reading. | Selecting a missing variable raises. Raster accessors can validate georeferencing and common grids. The paired segmentation reader checks actual image/label grid equality, label range, ignore values and finite prepared imagery. Coverage and split membership remain the project’s responsibility. |
| Are the numbers what this model learned? | A provider can harmonize values, and the model configuration can specify bands and normalization. The user still has to select the intended product, transform and target mapping. | The preprocessor selects bands in order and can decode, fill and standardize. The built-in Sentinel-2 source derives reflectance packing. A hand-supplied tree can claim the right band name and carry a different numerical representation. |

[rslearn config validators][rs-config] · [Required-input filtering][rs-filter] · [Sentinel-2 harmonization][rs-s2] · [GeoSave component specifications][gs-factory] · [Raster validation rules][gs-rules] · [Paired raster reader][gs-pairs]

**The same stored value produced two different model inputs.** I supplied GeoSave’s DensePreprocessor with a chunked, georeferenced `uint16` band called `B04`, filled with `2000`. With a scale factor of `0.0001`, zero offset and a fill declaration, it produced `0.2`. Removing those attributes produced `2000.0`. Both results had the same grid, Dask chunks and `float32` dtype. Both calls succeeded. Each result is consistent with its input metadata. Only the first matches a model trained on that reflectance convention. I also ran rslearn’s DatasetConfig on a raster declaration with no band sets and one declaring a `uint16 B04` band. It rejected the first and accepted the second without reading a file. Together the probes explain why a correct dataset declaration and a valid runtime type cover different risks. [GeoSave dense preprocessor][gs-prep] · [rslearn band-set and layer validation][rs-config]

**Let the release state its input assumptions.** Start with the properties its preprocessor relies on, including required nodes, ordered bands, accepted stored or decoded representations, and any grid or time relationships the model actually needs. Apply those checks to a representative training sample and to caller-supplied inference rasters. Keep labels, ignore IDs and split policy in the training project. The existing preprocessor and raster rules provide places to run those checks. Add a reusable declaration only when two consumers need to share it. For a model trained on packed Sentinel-2 data, a missing scale should produce an actionable error before the first model call. A project that deliberately accepts decoded reflectance should be able to say so. Metadata alone cannot detect a file whose producer supplied plausible but false values. [Preprocessor contract][gs-prep-base] · [Raster validation rules][gs-rules]

## Why quick training is the first priority

GeoSave already has a trainer, model assembly, optimizers, metrics, augmentation and checkpoint support. The Dynamic World notebook also calls `Trainer.fit` on real optical imagery with human annotations. It teaches the reader how to own the code. What is missing is a **freshly generated geospatial project whose supplied Dataset, DataModule, LightningModule and release script agree all the way through**. Naming another training command would leave that problem intact. [Lightning starter](../../advanced/training.md) · [Dynamic World notebook][gs-nb] · [Generated recipe status][gs-recipes]

I generated two clean workspaces. The Lightning boilerplate finished a CPU epoch and saved a checkpoint after four optimizer steps on synthetic features. For supervised segmentation I wrote tiny, aligned four-band GeoTIFFs and masks to the configured paths and selected the bundled small CNN and U-Net to avoid downloading foundation weights. The Dataset successfully produced `image`, `target`, `transform` and `crs`. The first training step stopped at `batch["inputs"]` with `KeyError: 'inputs'`. The sample is flat and the Module reads a nested mapping. The generated publication script also exports the chain, while the generated raster server loads a full pipeline. Completing that handoff would let someone use the trained model without reconstructing its preprocessing. Both pieces already exist in the library. [Dataset output][gs-pairs] · [Training step][gs-train-step] · [Generated publisher][gs-publisher] · [Generated server][gs-server]

I also ran rslearn’s offline segmentation integration tests. One trained for an epoch from its fixture dataset. The other exercised prediction separately and reopened the written 32 × 32 output layer to check its shape and class IDs. Those tests establish a working path on prepared data. The larger online Seattle–Portland tutorial adds provider acquisition and a pretrained encoder. [Upstream segmentation tests][rs-seg-test]

rslearn is clearer here because users can follow one configured path from named layers to a Task and on to a georeferenced prediction. GeoSave has its own advantage **inside the model**. A ModelChain exposes its input names and a diagram of the resolved stages. The component catalog can show compatible neighboring stages. GeoSave’s weak spot is the path *around* the model, where a reader has to look in several files to learn which bands, target, preprocessing, output classes and checkpoint belong together. A printed example showing one actual sample beside the model inputs and the resulting map would explain more than another architecture diagram alone. [rslearn model configuration][rs-model-config] · [GeoSave ModelChain][gs-chain] · [Component catalog][gs-components]

## Important gaps in the core mechanism

I would prioritize a mechanism when its absence can make a result wrong, make an experiment impossible to reproduce, or force each project to rebuild the same geospatial operation. These priorities are proposed engineering choices.

| Priority | What rslearn provides and where GeoSave falls short | Smallest useful GeoSave change and proof |
| --- | --- | --- |
| **1. Finish one real training-to-map workflow** | rslearn’s segmentation path binds source layers, targets, training and a prediction writer. GeoSave’s paired reader and released inference both work in isolation, but its generated sample breaks at the first training step. | Align the existing flat sample across training and validation. Use a small, pinned set of georeferenced pairs with separate scene splits. Fit a CPU baseline, reload its checkpoint in a fresh process, export the full pipeline and compare predictions on a held-out scene, including grid, nodata and class IDs. [rslearn segmentation integration][rs-seg-test] · [GeoSave recipe][gs-recipes] |
| **2. Check input meaning at the model boundary** | rslearn combines layer declarations, source-specific conversion and model input selection. GeoSave checks several pieces but caller-supplied rasters can bypass the assumptions of the release’s ingestor. | Compare the same known patch through the training reader, ingestor output and a saved file. Require equal prepared values, band order, mask and grid within the product’s declared tolerance. Include a deliberately incompatible file that fails before inference. [rslearn model input][rs-input] · [GeoSave preprocessing][gs-prep] |
| **3. Preserve sample identity and split provenance** | rslearn persists named windows, item groups, time ranges and split tags. A GeoSave project can use STAC or a table, but a chip layout identifies pixel positions only. Different projects must establish their own links between scenes, labels and model runs. | First publish a project-owned example table with a stable scene or annotation ID, source Items or file revisions, label revision, grid reference, interval, split group and split. Reopen it in another process and recreate the same pair. Verify overlapping chips or multiple annotations of one scene obey the intended grouping. [rslearn dataset format][rs-format] · [GeoSave sample design](samples-chips.md) |
| **4. Make multi-source and temporal preparation repeatable** | rslearn selects groups by space and time, can store input items once, and tracks completed materialized layers. It also offers cloud-aware compositors and can stack multiple groups for training. GeoSave has STAC search, grids, masking, temporal operators and explicit Zarr writes. The release ingestor interface returns a list of acquisitions, and the built-in dense path chips a common grid. The cross-source matching policy still belongs to each project. | Demonstrate one real join, such as optical imagery and a static elevation raster against the label grid. Record date selection, resampling and missing-input policy. Repeat after interruption from the recorded source selection. Add reusable preparation or cache logic when another project needs the same behavior. Record changes to inputs or processing when reusing an artifact. [rslearn materialization][rs-manage] · [Compositors][rs-composite] · [GeoSave grid loading][gs-load] · [Open sampling decisions](../open-decisions.md#sampling-and-stores) |
| **5. Complete task-specific targets and outputs as demand warrants** | rslearn connects classification, detection, scalar and dense regression, per-pixel temporal tasks, embeddings and multi-task models to concrete sample and output behavior. GeoSave has classification and regression heads and project recipes, while its built-in raster inference is strongest for dense segmentation and regression. Reading vectors or polygonizing a map covers only part of a detector’s job. | Pick the next task from a real project. For polygon labels in segmentation, prove class mapping and rasterization on the exact label grid. For detection, prove box coordinates through cropping and augmentation, then merge overlapping predictions back into correctly placed features. A new head alone would leave both problems unresolved. [rslearn tasks][rs-tasks] · [Detection integration][rs-detect-test] · [GeoSave recipe status][gs-recipes] · [Vector rasterization entry point][gs-vector] |

A useful first sample record can be an ordinary table row. For land cover, a row identifies the annotation and its revision, the image it labels, the grid to read, and the split assigned to their scene group. Many chips can refer back to that one row. A new canopy-height label for the same image gets its own record. A new chip stride changes the chip layout. Neither operation requires inventing a new satellite observation or assigning the original scene a new split. At evaluation time the project can trace a reported metric to its observations, ground truth and contributing pixels. [GeoSave sample design](samples-chips.md) · [rslearn stored window and item metadata][rs-format]

For a team running thousands of repeated areas of interest, priority 4 can move ahead of adding another training method. The scarce resource might be provider reads, repeated reprojection, GPU idle time or space taken by prepared windows. GeoSave’s lazy reads and rslearn’s materialization each move costs to a different point in the workflow. Measure network bytes, repeat-epoch throughput and storage on the same scenes before choosing a shared cache or claiming a performance advantage. A completed-layer marker proves a write was recorded. Detecting a changed processing recipe requires additional evidence. [rslearn materialization logic][rs-manage] · [GeoSave chunked prediction][gs-pipeline]

## What I would build first

Start with **one real land-cover baseline that a newcomer can reproduce from a fresh workspace**. Use already prepared image–label pairs so a failed fit can be diagnosed independently of credentials, catalog availability and upstream reprocessing. Give each scene a stable ID and split it before chipping. Show the prepared values of one known pixel, train the small model, reload the full release and predict the held-out scene. The handoff is complete when a colleague can open the output in xarray or a GIS and recover the expected grid and class legend. This would test several of GeoSave’s most valuable promises in one short run. [Paired reader][gs-pairs] · [Release API][gs-release] · [Dense products][gs-products]

Then let the **same model** accept a scene obtained through Sentinel-2 ingestion and the same scene reopened from a file. Show exactly which metadata makes them interchangeable. Only then add a second product or modality, using the same scene records to discover which selection, caching and validation behavior genuinely repeats. A shared abstraction earns its place when two independent callers otherwise have to agree on the same fact by hand.

For a team starting with areas and dates that wants supported sources aligned, trained on and mapped through one configured workflow, I would choose rslearn today. For a researcher starting with existing rasters or PyTorch code who expects to change the method, share the trained result and contribute what others can reuse, I would choose GeoSave. The first training recipe should demonstrate that advantage in practice. A new user should be able to run the baseline, change one part in their workspace and hand a colleague a pipeline that reproduces the map.

## Evidence and limits

During the review, the GeoSave working tree also gained draft change and prompt pipelines and a direct-call raster pipeline whose product can be a Dataset or a GeoDataFrame. Four additional focused tests passed for two-date change, georeferenced prompts, vector output and the current restriction of release export to RasterPipeline. These additions broaden inference. The generated training Dataset and Module still disagree about the batch keys. [Release and inference design](release-inference.md)

The comparison uses GeoSave `008d6f3e` and rslearn `2956a80c`. Five focused GeoSave tests passed for native-grid lazy loading, lazy standardization, paired-raster reading, prediction without an ingestor and release/prediction equivalence. The two rslearn segmentation tests passed on CPU with its locked parser and Lightning versions in a temporary environment. The GeoSave boilerplate and segmentation probes used freshly generated workspaces. I inspected the Dynamic World notebooks and the upstream online quickstart without rerunning those larger examples. These checks establish workflow behavior. Runtime, memory, cloud cost and model accuracy would each require a matched benchmark.
